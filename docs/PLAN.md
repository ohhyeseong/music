# 음악 발견 앱 — 검토용 계획 v0.1

상태: **2026-10-21 사용자 승인 후 MVP 구현.** 실제 음악 검색·일부 곡 단위 장르 보강과 Android AAB 빌드를 확인했다. 실제 분위기 데이터 확대·데이터 이용 허가·기기 검증·스토어 출시는 남아 있다. 최신 검사 결과는 `VALIDATION.md`를 따른다.

## 제품 목표

노래를 검색하고 '이 곡은 어떤 장르인가', '어떤 분위기인가', '함께 들으면 좋은 곡은 무엇인가'를 이해한 뒤 플레이리스트로 저장한다. 가칭은 **결 / GYEOL**이며 이름 확정이나 상표 확인은 하지 않았다.

대상은 한국어 UI를 사용하는 국내·해외 음악 청취자다. 국내·해외 모두 포함하는 범위는 사용자가 확인했다. 세부 장르 기준은 대표곡과 데이터 출처를 확인하며 보완한다.

예상 흐름:

1. 곡명·아티스트명으로 검색한다.
2. 동명이곡의 아티스트·앨범 정보를 보고 곡을 선택한다.
3. 출처가 있는 장르 설명과 분위기 태그를 확인한다.
4. 'Nu jazz 태그가 겹칩니다', '차분한 분위기 태그가 같습니다' 같은 추천 이유를 읽는다.
5. 추천곡을 선택해 내 플레이리스트에 저장하고 순서를 편집한다.

표현 예: 곡 단위 근거가 충분할 때만 '이 곡의 주요 장르는 Nu jazz입니다'라고 안내한다. 아티스트 태그만 있다면 '아티스트 정보에 Nu jazz 태그가 있습니다. 이 곡의 장르는 추가 확인이 필요합니다'라고 구분한다. 분위기 태그가 없으면 임의로 생성하지 않는다.

## 기술 선택과 선행 검증

- 프런트: Next.js + TypeScript. Tailwind CSS와 접근성 있는 기본 UI 컴포넌트 사용을 제안한다.
- 백엔드: NestJS REST API + TypeScript + OpenAPI.
- DB: MySQL 8.4 LTS + Prisma 마이그레이션을 제안한다. 로컬 개발용 컨테이너를 사용하고 테스트 DB를 별도로 둔다.
- 저장소: `apps/web`, `apps/api`, `packages/contracts`를 둔 npm workspaces. 별도 빌드 오케스트레이터는 필요할 때만 추가한다.
- Android: Next.js의 정적 내보내기와 Capacitor 조합을 먼저 검증한다. 서버 렌더링·서버 액션에 핵심 기능을 의존시키지 않는다. Next.js 자체만으로 Play Store용 앱이 만들어지는 것은 아니다.
- Node·프레임워크·ORM·Android SDK 버전은 구현 시작 시 공식 지원 범위와 현재 환경을 확인한 뒤 고정한다.

### 데이터 확보가 첫 번째 기술 검증이다

곡 검색·외부 링크는 Apple iTunes Search API, 상세 태그 보강은 MusicBrainz를 사용했다. 앱의 프록시 경로에서 실제 API를 확인하고 US 검색 시장을 기본으로 채택했다. 커버는 Apple의 홍보 콘텐츠 사용 조건 때문에 자체 그래픽을 사용한다. **일부 곡만 세부 장르 근거가 확보됐고, 실제 분위기 태그는 아직 없다.** 장르 연결은 MusicBrainz supplementary data의 CC BY-NC-SA 3.0 조건이므로 공개·상업 출시 전 이용 허가 검토가 필요하다. Spotify 의존성은 없다.

- 국내·해외·세부 장르·동명이곡을 포함한 대표곡으로 검색 결과, 곡 단위 장르, 요청 제한, 오류 응답을 확인한다.
- '뉴재즈'는 Nu jazz와 new jazz의 혼동 가능성이 있어 사용자의 대표곡과 데이터 출처로 구분한다.
- ISRC가 있으면 우선 대조하고, 제목·아티스트·길이를 보조로 사용한다. 애매한 후보를 자동으로 같은 곡에 합치지 않는다.
- 공급자가 곡 단위 분위기나 세부 장르를 주지 않으면 정보 부족을 표시한다. 임의 분류나 아티스트 정보의 확정 전용은 하지 않는다.
- 분위기 추천은 출처가 있거나 직접 검수한 태그가 있는 곡에 한정한다. 데모용 검수 카탈로그는 실제 API 데이터와 명확히 구분한다.
- 검증된 데이터 범위가 제품 요구를 충족하지 못하면 공급자 변경·라이선스·검수 카탈로그 운영 범위를 보고하고 설계 변경 승인을 받는다.

## 테스트 원칙

로직 구현마다 관련 부분 테스트를 하고, 전체 로직 완성 후 전체 테스트를 실행한다.

- **단위:** 검색 정규화, 장르 별칭의 모호성, 공급자 데이터 매핑, 근거 수준, 추천 점수·필터·안정적인 순서, 인증 입력 검증.
- **통합:** 실제 MySQL 테스트 DB에 마이그레이션 후 API 확인. 중복 추가, 다른 사용자의 접근, 만료 세션, 삭제, 순서 편집 충돌과 롤백을 검증한다. SQLite로 MySQL 검증을 대체하지 않는다.
- **웹 E2E:** Playwright로 검색 → 곡 선택 → 장르 설명 → 추천 → 로그인 → 플레이리스트 생성·저장·재조회·정렬을 확인한다. 빈 결과·외부 API 오류도 확인한다.
- **외부 API 확인:** 재현 가능한 fixture 기반 테스트와 별도로 실제 공급자 smoke test를 실행한다. fixture 통과를 실제 연동 성공으로 표현하지 않는다.
- **전체:** lint, 타입 검사, 모든 단위·통합·E2E, 프로덕션 빌드, API/웹 재시작과 기능 요청. 테스트 수·실패·건너뜀·미실행을 기록한다.
- **Android:** 정적 자산 포함, HTTPS API 연결, 뒤로가기, 키보드, 재시작 후 인증, 접근성, AAB 생성, 실제 기기 또는 에뮬레이터에서 핵심 흐름 확인. SDK나 기기가 없으면 미검증으로 남긴다.

테스트에 쓰는 계정·DB·이미지·음악 정보는 실제 사용자 데이터와 분리한다. 테스트는 개발용 DB를 초기화하지 않으며, 파괴적인 테스트 명령에는 테스트 DB 여부 확인을 둔다.

## 검토할 제안

1. 검색 → 출처 있는 장르/분위기 → 유사곡 → 내 플레이리스트를 초기 범위로 진행한다.
2. Next.js / NestJS / TypeScript / MySQL, Prisma, npm workspaces를 사용한다.
3. Android는 Capacitor 방식의 선행 검증 후 확정한다.
4. 첫 추천은 태그 기반으로 구현하며, 근거 없는 AI 장르 판정·전체 음원 재생은 포함하지 않는다.
5. 시각 방향은 `DESIGN_REFERENCES.md`의 다크·라일락·라임 팔레트와 앨범 중심 화면으로 시작한다.
